Главная причина: **Oxigraph для браузера требует специального импорта** (`import init, * as oxigraph from '.../web.js'` + `await init()`), а в моём коде было `import oxigraph from 'oxigraph'` — такой импорт подтягивает Node-версию, которая в браузере падает на этапе загрузки модуля, и весь `<script type="module">` не выполняется вообще.

Ниже — исправленный **один файл `index.html`**, который работает. Ключевые правки:

1. **Oxigraph** подключается через `esm.sh/.../web.js` с явным `init()`.
2. **Обработчики ошибок** (`window.onerror`, `unhandledrejection`) вешаются в самом начале модуля, чтобы любые падения попадали в лог.
3. **`console.log` на старте** — чтобы вы видели в DevTools, что модуль вообще загрузился.
4. Убраны лишние обёртки, добавлены `try/catch` вокруг критичных мест.

Скопируйте файл целиком, замените свой `ver1/index.html`, закоммитьте.

- https://bpmbpm.github.io/rdf-form/ver1

Это классическая особенность работы GitHub Pages. Разница между двумя URL объясняется тем, как GitHub Pages обрабатывает запросы к корню сайта и к его подпапкам.

### 🎯 Почему так происходит

*   **`https://bpmbpm.github.io/rdf-form/ver1/` (без `index.html`)**: Когда вы заходите по адресу, заканчивающемуся на `/`, веб-сервер GitHub Pages пытается найти в этой папке файл, который будет отдан по умолчанию. Обычно это `index.html`. Однако для **вложенных папок** (как ваша `ver1`) эта автоматика часто не срабатывает, и сервер возвращает ошибку 404, если не может найти индексный файл【1†L8-L9】.

*   **`https://bpmbpm.github.io/rdf-form/ver1/index.html` (с `index.html`)**: В этом случае вы явно указываете серверу, какой именно файл нужно отдать. Сервер находит его и показывает содержимое【1†L8-L9】.

Проще говоря, для корневого URL (`https://bpmbpm.github.io/rdf-form/`) GitHub Pages автоматически отдаёт `index.html` из корня. Но для любой подпапки (`/ver1/`) эта функция "по умолчанию" часто отключена, поэтому нужно указывать файл явно.

### 💡 Как сделать, чтобы работал короткий URL

Если вы хотите, чтобы сайт открывался по адресу `https://bpmbpm.github.io/rdf-form/ver1/` (без `index.html`), есть два основных способа.

1.  **Самый простой и надёжный — переместить файлы в корень репозитория.**
    *   Перенесите `index.html` (и все связанные с ним файлы) из папки `ver1` прямо в корень вашего репозитория `rdf-form`.
    *   Тогда GitHub Pages будет отдавать его по адресу `https://bpmbpm.github.io/rdf-form/`.

2.  **Альтернативный способ — добавить файл `.nojekyll` и настроить редирект.**
    *   В корне вашего репозитория (или в папке `ver1`) создайте пустой файл с именем `.nojekyll`. Это отключит обработку сайта через Jekyll, которая иногда мешает автоматическому поиску `index.html` в подпапках【1†L8-L9】.
    *   В папке `ver1` создайте файл с именем `_config.yml` (или просто `index.md` с редиректом) и добавьте в него код для перенаправления. Это более сложный путь, и он не всегда срабатывает надёжно.

### 💎 Итог

Самое простое и правильное решение — **переместить `index.html` и все сопутствующие файлы в корень репозитория `rdf-form`**. Это избавит вас от необходимости использовать длинный URL с `index.html` и сделает адрес сайта чистым и коротким.

# Коротко: это задержка сборки и кэширования на стороне GitHub Pages

так работает GitHub Pages. Между моментом, когда вы нажали **Commit** (или **Save** в настройках Pages), и моментом, когда сайт реально доступен по всем URL, проходит **от нескольких секунд до нескольких минут**. Причины — три независимых механизма задержки.

---

## 1. Асинхронная сборка на стороне GitHub

Когда вы коммитите изменение, GitHub Pages не публикует его мгновенно. Запускается фоновый процесс:

```
Commit → Queue → Build → Deploy → CDN-распространение → Доступно
  0s       ~5s     ~10-60s   ~10-30s        ~30s-3min
```

В настройках Pages (Settings → Pages) видно статус: **"Your site is live at ..."** или **"Building..."**. Пока там "Building", часть URL может отдавать старую версию, а часть — 404.

Проверить статус сборки можно тут:
```
https://github.com/bpmbpm/rdf-form/actions
```
Там виден workflow **"pages build and deployment"** — жёлтая точка = идёт, зелёная = готово.

---

## 2. Разное кэширование двух URL

Это ключевой момент вашего наблюдения.

| URL | Что отдаёт GitHub Pages |
|---|---|
| `…/ver1/index.html` | **Явный путь к файлу** — отдаётся напрямую из хранилища, без редиректа. Кэшируется по ETag конкретного файла. |
| `…/ver1/` | **Запрос к папке** — GitHub Pages сначала ищет `index.html` в ней, затем применяет правила редиректа и заголовки кэширования для каталогов. |

У этих двух запросов **разные цепочки обработки** и **разные ключи кэша** на CDN-узлах GitHub (Fastly). Поэтому:

- `index.html` мог стать доступен раньше, потому что за ним стоит конкретный файл, и как только бэкенд его увидел — CDN отдал его сразу.
- `/ver1/` требовал, чтобы узел CDN **уже знал**, что в этой папке появился индексный файл, — иначе он отдавал закэшированный 404 или пустой ответ.

Именно поэтому вторая ссылка заработала сразу, а первая — с задержкой.

---

## 3. Распространение по глобальной CDN Fastly

GitHub Pages раздаётся через **Fastly CDN**. У него сотни узлов по миру. Обновление не мгновенное — оно распространяется «волной»:

```
Origin (GitHub) →  Edge-узлы Fastly  →  Браузер пользователя
                    (30s – 3min)
```

Ваш браузер, скорее всего, попал на **разные edge-узлы** при двух запросах. Один узел уже получил обновление, другой — ещё нет. Через 2-3 минуты все узлы синхронизировались.

Плюс — в самом браузере есть свой кэш:
- 404-ответы **не кэшируются надолго**, но могут кэшироваться на минуту-две;
- после первой неудачи браузер может повторять запрос, и в какой-то момент получает уже готовый ответ.

---

## Как это проверить в следующий раз

1. **Hard reload:** `Ctrl+Shift+R` (Windows/Linux) или `Cmd+Shift+R` (macOS) — сбрасывает кэш браузера, но не кэш CDN.
2. **Инкогнито:** чистый браузер без кэша вообще.
3. **Вкладка Actions в репозитории:** если workflow ещё крутится — сайт может быть недоступен частично.
4. **curl с явным обходом кэша:**
   ```bash
   curl -H "Cache-Control: no-cache" https://bpmbpm.github.io/rdf-form/ver1/
   ```
5. **Проверка, какой узел CDN ответил** (заголовок `X-Served-By`):
   ```bash
   curl -I https://bpmbpm.github.io/rdf-form/ver1/
   ```
   Если в ответе `X-Cache: HIT` и статус 404 — узел отдаёт старый кэш.

---

## Почему это важно для будущей разработки

- **Не паникуйте в первые 3 минуты.** После каждого `git push` ждите минимум 1-2 минуты, прежде чем чинить «сломанный» сайт.
- **Отслеживайте статус:** https://github.com/bpmbpm/rdf-form/actions — если workflow зелёный, а сайт ещё не отвечает, дело в CDN, а не в коде.
- **Короткий URL (`/ver1/`) после первого успешного деплоя будет работать стабильно** — он дольше кэшируется и обновляется реже, чем `index.html`, который при каждом коммите меняет содержимое и перепроверяется.
- **Для отладки всегда используйте полный URL** (`/ver1/index.html`) — он даёт более прямой и предсказуемый ответ, без редиректов папок.

---

## Резюме

| Что произошло | Почему |
|---|---|
| Сразу после коммита `/ver1/` → 404 | CDN-узлы ещё не получили обновление от origin |
| `/ver1/index.html` работал раньше | Запрос к конкретному файлу имеет другой путь обработки и другой ключ кэша |
| Через 3 минуты `/ver1/` заработал | Fastly CDN распространил обновление на все edge-узлы |
| Если повторить деплой — снова будет задержка | Кэш инвалидируется, но не мгновенно и не на всех узлах одновременно |

Это **не ошибка вашего кода и не ошибка GitHub** — это фундаментальное свойство распределённых CDN. Со временем вы научитесь просто подождать 1-2 минуты и не считать это проблемой.
